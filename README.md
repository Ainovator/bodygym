# Feetwork

Дневник силовых тренировок: программы → подходы в зале → история → прогресс.
Рабочий end-to-end MVP на Go, PostgreSQL и React. По умолчанию — чёрно-медная тема с тёплым светлым текстом и графитовыми волнами на фоне. Дополнительно доступны светлая тема, мобильная навигация и устанавливаемая PWA.

## Быстрый запуск

Нужен Docker Desktop / Docker Engine с Compose v2.20+; локальные Go и Node для этого способа не нужны.

```sh
docker compose up --build
```

Открыть **http://localhost:3000**. Миграции и seed применяются автоматически после готовности PostgreSQL, затем запускаются API и Nginx.

Также доступны:

- API: `http://localhost:8088/api/v1`
- Проверка готовности: `http://localhost:8088/readyz`
- PostgreSQL: `localhost:5438`, база/пользователь `feetwork`, локальный пароль `feetwork_local`.

Порты выбраны так, чтобы не занимать обычные 5432, 8080 и 5173. Меняются через `APP_PORT`, `API_PORT`, `POSTGRES_PORT` в `.env`.
Для запуска с настройками скопируйте `.env.example` в `.env`. Без файла работают локальные значения по умолчанию.

Это **режим одного демо-пользователя без авторизации**. Все обращения используют фиксированный demo user ID. Порты привязаны к loopback. Публичный многопользовательский сервис требует аутентификации и привязки запросов к подтверждённой личности; переключателя пользователя через заголовок здесь нет.

Сразу после первого запуска доступны:

- Демо-профиль «Алексей», масса 86.4 кг.
- 24 упражнения с отдельными анатомическими иллюстрациями, описанием, 4 шагами техники, ошибками, мышцами, оборудованием и нормой отдыха.
- Каталог из 236 реальных моделей шести брендов: Life Fitness, Hammer Strength, Matrix, Concept2, ICG и SCIFIT. Силовые, кардио, скамьи и стойки с локальными изображениями производителей и ссылками на источники. Пополняемый справочник, не исчерпывающий перечень всех моделей.
- Программы «Грудь + трицепс», «Спина + бицепс», «Ноги / общая силовая».
- 9 явно обозначенных демонстрационных тренировок и 8 измерений массы тела. Даты отсчитываются от первого применения seed; интерфейс рассчитывает реальные показатели из этих записей.

## Что реализовано

- CRUD программ, поиск упражнений по названию/slug, фильтр по группе мышц, перестановка упражнений, настройки подходов, повторений и отдыха.
- Сегодня: выбор программы, план, прошлые результаты, недельная лента, месячные итоги.
- Транзакционный старт: снимок программы и запланированные подходы с прошлым весом/повторами.
- Одна активная тренировка на пользователя. Повторные и параллельные запросы старта возвращают ту же тренировку.
- Запись веса/повторов, кнопки ±2.5/±5 кг, отметка подхода, дополнительные RIR/RPE, добавление и удаление подходов.
- Автоподстановка веса/повторов в следующий подход; вручную изменённый следующий подход не перезаписывается.
- Таймер отдыха по абсолютному времени: автозапуск, +30 секунд, пропуск, восстановление после закрытия страницы.
- Финальный экран: длительность, завершённые подходы, объём, оценка калорий с диапазоном, новые рекорды и заметки.
- История с датами и пагинацией, подробности каждой тренировки.
- Обзор за месяц; графики тренировок, объёма и калорий по неделям; API также возвращает агрегацию по месяцам.
- Прогресс упражнения: максимальный вес, Epley 1RM, объём по дням, лучшие повторы на каждом весе, изменение максимума в текущем месяце относительно прежнего.
- Запись массы тела и график. Старое измерение не меняет актуальный вес профиля; начатая тренировка сохраняет свой снимок массы тела.
- Каталог `/catalog/exercises` и `/catalog/machines`: поиск по названию, мышцам, оборудованию и модели; фильтры по бренду, виду оборудования и мышцам; страницы по 24 модели с сохранением фильтров и страницы в URL; карточки тренажёров и переходы к связанным движениям.
- Локальные шрифты, SVG/WebP-иллюстрации, фотографии оборудования и PNG-иконки PWA; внешние CDN для интерфейса не нужны. После первого онлайн-открытия каталог и изображения доступны офлайн.
- Анатомические иллюстрации созданы встроенным `image_gen`; итоговые промпты и пути файлов — [docs/exercise-image-prompts.json](docs/exercise-image-prompts.json). Источники фотографий моделей — [docs/equipment-image-sources.md](docs/equipment-image-sources.md).


HTTP-слой не содержит бизнес-логику. `service` зависит от интерфейса `repository.Store`; PostgreSQL реализует его. `context.Context` проходит через каждый вызов. SQL параметризован; ORM нет.

Старт блокирует строку пользователя и атомарно создаёт всю тренировку. Изменения подходов и завершение блокируют строку сессии; завершённую тренировку нельзя изменить. Завершение идемпотентно и записывает итог калорий и рекорды один раз. POST добавления подхода принимает клиентский UUID для безопасного повтора после потери ответа. Удаление программы сохраняет историю, название и параметры упражнений в сессии.

Логи — JSON через `slog`, с request ID, длительностью и статусом. Есть ограничения размера JSON, HTTP timeouts, readiness/liveness, CORS по списку, проверка UUID, диапазонов и неизвестных полей. Backend работает в контейнере без root; Nginx выставляет CSP и защитные заголовки.

## Модель данных

Все PK — UUID с `gen_random_uuid()`, даты — `timestamptz`, вес — `numeric`. Миграция добавляет FK, CHECK, уникальность и индексы.

| Таблица | Назначение и связи |
| --- | --- |
| `users` | Профиль, актуальная масса тела |
| `exercises` | Каталог; техника, мышцы и ошибки в JSONB; уникальный slug |
| `exercise_media` | Несколько image/video URL на упражнение, упорядоченных по position |
| `workout_templates` | Программы пользователя |
| `workout_template_exercises` | Упражнения и целевые параметры программы |
| `workout_sessions` | Время, масса тела, название-снимок, калории, рекорды и заметки |
| `workout_session_exercises` | Снимок порядка, повторений и отдыха; тайминги упражнения |
| `workout_sets` | Вес, повторы, RIR/RPE, выполнение, тайминги и заметки |
| `body_weight_entries` | Измерения массы тела |

Удаление пользователя каскадно удаляет его данные; удаление сессии — упражнения и подходы. Для `template_id` в истории — `ON DELETE SET NULL`. Использованные упражнения каталога защищены от удаления FK; их media удаляются каскадно.

Основные индексы: `(user_id, started_at DESC)`, `(session_exercise_id)`, `(exercise_id)`, `(user_id, measured_at DESC)`. Частичный unique index на пользователя с `finished_at IS NULL` защищает от второй активной тренировки.

## API

Префикс: `/api/v1`. Данные возвращаются напрямую; создание — `201`, удаление — `204`.

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| GET | `/me` | Демо-профиль |
| GET | `/exercises` | Каталог |
| GET | `/exercises/{id}` | Упражнение и media |
| GET | `/exercises/{id}/previous` | Последняя завершённая тренировка упражнения, только выполненные подходы |
| GET, POST | `/workout-templates` | Список / создание |
| GET, PUT, DELETE | `/workout-templates/{id}` | Чтение / замена / удаление |
| POST | `/workouts/start` | Транзакционный старт из `template_id` |
| GET | `/workouts/active` | Активная тренировка либо `null` |
| GET, PATCH | `/workouts/{id}` | Тренировка / заметки и масса тела активной сессии |
| POST | `/workouts/{id}/finish` | Идемпотентное завершение и финальные итоги |
| PATCH, DELETE | `/sets/{id}` | Изменение / удаление подхода |
| POST | `/session-exercises/{id}/sets` | Ещё один подход; JSON `{}` или `{"id":"UUID"}` |
| GET | `/history` | `page=1`, `limit=20` (максимум 100), `from`, `to` |
| GET | `/stats/overview` | Суммы + `weeks` и `months`; фильтры `from`, `to` |
| GET | `/stats/exercises/{id}` | PR, best reps per weight, time series |
| GET | `/stats/body-weight` | Измерения массы тела по времени |
| POST | `/body-weight` | Новое измерение и актуализация профиля |

Вне префикса: `GET /healthz`, `GET /readyz` (503 при недоступной БД).

Даты фильтров: `YYYY-MM-DD` или RFC3339. `from` включительно; `to` с датой включает весь этот день UTC, `to` с временем — исключительная граница. Группировка по дням/неделям/месяцам — UTC, неделя начинается в понедельник. Длительность в API — секунды. `monthly_weight_change` сравнивает лучший вес текущего месяца с максимумом до начала месяца; при отсутствии базы возвращается 0.

```json
POST /api/v1/workouts/start
{"template_id":"22222222-2222-4222-8222-222222222221"}
```

```json
PATCH /api/v1/sets/{id}
{"weight_kg":82.5,"reps":10,"rir":2,"rpe":8,"completed":true}
```

`rir`/`rpe`: пропущенное поле сохраняет значение; `null` очищает. Время завершения подхода ставит сервер. Опциональный `started_at` должен находиться внутри текущей тренировки. Повторное `completed:true` не сбрасывает время выполнения; `false` очищает `completed_at`.

```json
POST /api/v1/workout-templates
{
  "name":"Верх тела",
  "description":"Спокойная силовая",
  "exercises":[{
    "exercise_id":"UUID из каталога",
    "target_sets":3,
    "target_reps_min":8,
    "target_reps_max":12,
    "rest_seconds":120
  }]
}
```

Порядок массива определяет порядок упражнений. Ограничения: 1–30 упражнений, 1–20 запланированных подходов, до 30 подходов после добавления, 1–100 повторений, 0–1000 кг снаряда, 20–500 кг массы тела, RIR 0–10, RPE 1–10, отдых 0–900 секунд.

Ошибки имеют вид:

```json
{"error":{"code":"validation_error","message":"Повторы: 1–100","request_id":"..."}}
```

Коды: 400 — JSON, 404 — запись, 405 — метод, 409 — завершённая сессия, 413 — тело больше 1 МБ, 415 — Content-Type, 422 — валидация, 500 — внутренняя ошибка. Детали БД в клиентский ответ не попадают.

## Offline и PWA

Production build создаёт service worker с версионируемым кэшем HTML, JS, CSS, шрифтов, иллюстраций и иконок. API service worker не кэширует. TanStack Query отдельно сохраняет прочитанные данные в localStorage на 7 дней.

Каждая правка подхода сначала попадает в устойчивую локальную очередь, затем отправляется последовательно. Новая правка во время запроса не теряется. Даже неполный ввод вроде `82,` или пустого поля хранится отдельно и переживает reload. После восстановления сети очередь отправляется автоматически. Ошибки валидации показаны и остаются в очереди до исправления.

Завершение разрешено только при корректных полях и успешной отправке всех подходов. Заметки хранятся локально и отправляются при завершении. Создание/удаление программ и подходов, начало/завершение тренировки и запись массы тела требуют сети. Offline-доступ относится к уже открытой/кэшированной тренировке. Очистка данных браузера удалит ещё не отправленные изменения.

Таймер опирается на сохранённый deadline, поэтому не теряет время при сворачивании. Вибрация при завершении отдыха зависит от поддержки браузера; системные фоновые уведомления не реализованы. Обновление service worker не принудительно перезагружает открытую тренировку.

Установка PWA: меню браузера → «Установить» / «На экран Домой». Service worker работает на localhost или HTTPS. Для доступа с физического телефона нужен доступный HTTPS-origin и корректная конфигурация размещения. Одновременное редактирование одного подхода на нескольких устройствах не объединяет значения: действует последняя серверная запись.

## Калории и 1RM

```
kcal/min = MET × 3.5 × bodyWeightKg / 200
```

MET активной части: isolation 4.0, machine_compound 4.5, compound 5.5, high_intensity 6.0; отдых 1.8. Множитель RPE: до 5 — 0.90; >5 до 7 — 1.00; >7 до 10 — 1.10; 10 — 1.15. Без RPE — 1.00.

Для завершённых подходов используются `started_at`/`completed_at`, если они заданы; иначе `reps × 3 + 10` секунд. Интервалы ограничены временем сессии, суммарная активная часть не превышает её длительность. Остаток — отдых. Текущий UI использует fallback-оценку длительности подхода. Повторы/вес незавершённых подходов не учитываются в объёме, рекордах и активных калориях.

API возвращает оценку и ориентировочный диапазон ±30%; это эвристика, **не статистический доверительный интервал**. UI округляет калории до десятков (`≈ 430 ккал`). При длительной забытой активной сессии время до нажатия «Завершить» считается отдыхом. Калории — модельная оценка, не измерение и не медицинская рекомендация.

Объём = сумма `weight_kg × reps` только выполненных подходов. Для упражнений с собственным весом введите внешнее отягощение; массу тела приложение автоматически к объёму не добавляет.

Epley: `weight × (1 + reps / 30)` для 1–15 повторений. Выше 15 оценка пропускается (0 в API); после 10 отмечена повышенная погрешность. PR фиксируются при завершении: максимальный вес, расчётный 1RM и повторы на уже использованном весе. Первые max weight / 1RM — начальные рекорды, UI подписывает «Первая отметка».

## Разработка

Текущие исправленные версии зависимостей требуют **Go 1.26+** (в пределах запрошенного 1.24+), Node.js 22.12+, npm и PostgreSQL 16. Использованы chi 5.3, pgx/v5 5.11, React 19, TypeScript strict, Vite 7, TanStack Query 5, Recharts 3.

```sh
docker compose up -d postgres
docker compose run --rm migrate

# терминал 1, по умолчанию localhost:8088 и БД localhost:5438
cd backend
go run ./cmd/api

# терминал 2, localhost:5178, /api проксируется на localhost:8088
cd frontend
npm ci
npm run dev
```

Go читает переменные окружения процесса, а не загружает `.env` автоматически. В Compose адрес БД и порт HTTP внутри контейнера задаются отдельно: `postgres:5432`, `:8080`. Для другого API-порта при разработке обновите proxy в `vite.config.ts`. В dev-режиме service worker не регистрируется; PWA проверяется через production Compose.

## Миграции и эксплуатация

Миграции выполняет отдельный одноразовый контейнер `migrate/migrate`. Ошибка миграции блокирует старт API. PostgreSQL хранит данные в named volume `feetwork_postgres_data`.

```sh
docker compose run --rm migrate             # применить новые up-миграции
docker compose logs -f backend frontend     # логи
docker compose down                        # остановить, сохранить БД
docker compose up -d --build                # обновить и запустить в фоне
```

Перед откатом миграций сделайте backup. Down-миграции присутствуют; schema down удаляет таблицы, demo down удаляет демо-пользователя и его данные. Не редактируйте уже применённые миграции для обновления реальной БД — добавляйте новые версии.

Статистика MVP агрегируется в сервисном слое по завершённым сессиям; история пагинируется в SQL. Для больших многопользовательских объёмов нужны SQL-агрегации/материализованные представления и измерение нагрузки. Для публичного размещения также нужны авторизация, HTTPS, секреты и резервное копирование. Docker Compose здесь настроен для локальной эксплуатации.

```sh
cd backend

cd ../frontend
```

Без локального Go:

```sh
docker compose run --rm backend-check
docker compose run --rm -e TEST_DATABASE_URL=postgres://feetwork:feetwork_local@postgres:5432/feetwork?sslmode=disable backend-check
docker compose run --rm backend-check sh -c 'go run golang.org/x/vuln/cmd/govulncheck@latest ./...'
```

Интеграционный Go-тест создаёт отдельного временного пользователя, проверяет rollback, конкурентный старт, planned sets, nullable PATCH, изоляцию пользователя, идемпотентность добавления/завершения, блокировку правок после finish, previous, историю и сохранение сессии после удаления программы. Временный пользователь удаляется. Без `TEST_DATABASE_URL` этот тест явно пропускается.

Frontend unit-тесты покрывают дробный ввод, диапазоны, локальное восстановление, повторы сетевых ошибок и новую правку во время уже отправленного запроса.

Playwright проверяет Desktop 1440px и Mobile 390px, навигацию, графики, темы, редактор программ, тренировку, offline/reload, таймер, синхронизацию, добавление/удаление подходов, завершение, историю, API и массу тела:

```sh
cd frontend
npx playwright install chromium
npm run test:e2e
```

**E2E изменяет демо-данные.** Для регулярных прогонов используйте отдельный Compose project/БД. Пример для Bash:

```sh
APP_PORT=3001 API_PORT=8089 POSTGRES_PORT=5439 docker compose -p feetwork-e2e up --build -d
cd frontend
E2E_BASE_URL=http://localhost:3001 npm run test:e2e
```

В PowerShell сначала задайте `$env:APP_PORT='3001'`, `$env:API_PORT='8089'`, `$env:POSTGRES_PORT='5439'`, затем те же команды Compose; перед тестами `$env:E2E_BASE_URL='http://localhost:3001'`. Скриншоты и список созданных ID сохраняются в `artifacts/`, HTML-отчёт — в `frontend/playwright-report/`.
